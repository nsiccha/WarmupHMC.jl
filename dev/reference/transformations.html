Scale operators ​

WarmupHMC.scale_data Function
julia
scale_data(L) -> (; diagonal, indices, reflections)

The plain-data form of a scale L the samplers learn: scale_options.diagonal or scale_options.adaptive of an adaptive_warmup_mcmc result or checkpoint, or a ContinuousNUTSState's scale. Every field is a fresh array (diagonal::Vector{Float64}, indices::Vector{Vector{Int}}, reflections::Vector{Vector{Float64}}), never an alias of L. scale_from_data rebuilds the operator.

L is H₁ ⋯ H_k · Diagonal(diagonal) with k = length(reflections), where H_i = I - 2 P_iᵀ r_i r_iᵀ P_i, r_i = reflections[i], and P_i selects the coordinates indices[i]. On a vector, in O(d · k):

  • y = L * z: y = diagonal .* z, then for i = k, …, 1, y[indices[i]] .-= 2 .* r_i .* dot(r_i, y[indices[i]]);

  • y = L \ x: y = copy(x), the same step for i = 1, …, k, then y ./= diagonal;

  • log|det L| = sum(log ∘ abs, diagonal) + sum(log(abs(1 - 2 dot(r_i, r_i)))), whose second sum is zero for the unit r_i a fit stores.

A Diagonal has no reflections. A product of two diagonals, which is what the :pathfinder option is after a diagonal init = (; position, squared_scale) (no Pathfinder run), has no reflections either, and its diagonal is the two factors' entrywise product. That product is rounded once per coordinate, so the rebuilt scale agrees with such an L to rounding, not bit for bit. Any other scale is an ArgumentError, including the :pathfinder option after a Pathfinder run, whose low-rank factor has no such form.

WarmupHMC.scale_from_data Function
julia
scale_from_data(data) -> L

Rebuild the scale that data describes, in the form scale_data returns: (; diagonal, indices, reflections), any object with those three properties. The result is a WarmupHMC.ScaleThenReflect (with no reflections for diagonal data) that FixedKernelNUTSState takes as metric and that answers L * z, L \ x, mul!, ldiv!, logabsdet and det without forming a d × d matrix. Its products, solves and the kernel built from it are bit-identical to those of the Diagonal or reflection scale data was taken from, and agree to rounding with a product of two diagonals. data is copied.

An ArgumentError names the offending entry when the data cannot describe such a scale: indices and reflections differ in length; a diagonal entry is not finite and positive; an index set is empty, leaves 1:length(diagonal), repeats a coordinate, or differs in length from its reflection; a reflection entry is not finite; or an index set is longer than the first. A fitted scale's index sets only shrink, and the product's work buffer is sized by the first one.

WarmupHMC.fit_gaussian_moments Function
julia
fit_gaussian_moments(draws; weights, max_reflections=16, maxiter=100, progress=nothing)

Fit a Gaussian moment summary to finite real d × N draws, one observation per column. Return (; mean, scale, diagnostics), all plain data, with newly owned arrays and no retained draws. scale_from_data(summary.scale) reconstructs a factor L of the approximate covariance L * L'. Inputs are never modified.

weights is a length-N vector of nonnegative finite masses with positive sum; it is normalized internally. Moments are population moments of this discrete distribution, without a sample-size or effective-sample-size correction. Both inputs are converted to Float64; unrepresentable moments are rejected.

The fit learns up to min(max_reflections, d-1) leading covariance directions by bounded power iteration, represented as successive Householder reflections. It then matches the weighted marginal variances in that rotated frame. No gradients, pilot, density evaluations, or sampler adaptation are involved. max_reflections=0 fits the original coordinatewise variances.

The weighted centered cloud is copied once. At fixed reflection and iteration bounds, work and temporary storage are linear in both d and N: work is O(d N (1 + max_reflections * maxiter)), workspace O(d N + d k + N), and returned storage O(d (1 + k)), where k ≤ max_reflections. No dense covariance is formed. A private fixed random stream initializes the iterations; the caller's random stream is untouched and repeated calls with the same inputs are deterministic.progress accepts a Treebars parent or backend, with counters for the fitted directions and the current direction's iterations.

diagnostics contains reflections, per-direction iterations, relative_residuals, converged, and effective_sample_size. converged means each fitted direction's relative eigen-residual is at most 1e-8; it does not certify covariance accuracy or that a leading eigenvector was found. Reaching maxiter returns the bounded approximation with converged=false, not an unreported retry. There is no retained iteration trace.

A finite reflection budget discards remaining cross-covariances, even for a Gaussian cloud. Close eigenvalues can require more iterations, and leading directions can miss narrow correlations. This is an empirical moment approximation, not an accuracy guarantee or a general posterior density fit. The mean is fitted independently of the reflection budget.

Zero marginal spread or a fitted direction whose spread is at floating-point roundoff is an ArgumentError, not a hidden variance floor. The roundoff test applies only after reflections and uses 8eps(Float64) * norm(weighted_cloud) per reflection in the normalized fitting frame. No regularization is added.

Partial centering ​

PartiallyCentered is re-exported from ReparametrizableDistributions.

PartiallyCentered ​

julia
PartiallyCentered(c)

A scalar normal location/scale coordinate system with centering c: x = c * loc + exp(c * log_scale) * z for standardized z. c = 0 is non-centered; c = 1 is centered. Intermediate centerings interpolate continuously. The object stores only c; adaptation belongs to the sampler. Use floating-point c when a sampler will update it.

WarmupHMC.Reparametrization Type
julia
Reparametrization(target, source, args...)

One coordinate's rule: map that coordinate's value from source coordinates into target coordinates. Both are PartiallyCentered.

  • target is the parametrization the wrapped problem is written in. It is FIXED — warm-up never touches it.

  • source is the parametrization the sampler works in. Warm-up REPLACES it at every restarting window (see PartiallyCentered).

Construct both with the same centering to start the sampler in the model's own parametrization and let warm-up move it from there.

args are the extra arguments the centerings need — for PartiallyCentered exactly two, the location and the log-scale, in that order. Each is either a constant number or a callable (a Function or a callable struct) applied to the whole parameter vector, so x -> x[9] reads the location off coordinate 9 and 0. pins it to zero. A log-scale may combine several coordinates, as in a scale mixture beta = s(θ) * z whose log(s(θ)) the callable computes.

A callable struct need not subtype Function (from WarmupHMC 0.2.15; before it, one that did not was silently used as a constant). A constant must be Real: IndexedReparametrization rejects an argument that is neither a Real nor callable at construction. Mixing constants and callables within ONE rule is fine; across the pairs of one IndexedReparametrization, see its concrete-type requirement.

The callables are applied to the sampler's SOURCE-coordinate vector as it was on entry: IndexedReparametrization writes its output into a copy, so no coordinate's rule ever observes another coordinate's transformed value. They also run under AD on every gradient evaluation (see ReparametrizedProblem), so keep them cheap and type-generic — index, arithmetic, exp/log, not Float64-annotated code or anything that mutates.

InverseFunctions.inverse returns the same rule with target and source swapped.

PartiallyCentered and the scalar transform come from ReparametrizableDistributions. Use floating-point centerings such as PartiallyCentered(1.0): adaptation writes fitted floating-point values back into the same pairs vector. By default, each restarting warm-up window scores 11 candidates over range(0, 1, 11) and updates the source centering; the target remains fixed. See CandidateScoringPlan and WindowSelectionPlan for custom scoring and selection.

See Reparametrization for an executed construction example.

WarmupHMC.IndexedReparametrization Type
julia
IndexedReparametrization(pairs)

A vector of index => Reparametrization(...) pairs for a ReparametrizedProblem. Each index identifies one scalar coordinate in the unconstrained position vector. Unlisted coordinates pass through unchanged; the wrapper sums the maps' log-Jacobians. An empty vector applies no map and does not infer a model's hierarchy.

Warm-up replaces each pair's source centering in place. Independent adaptive chains need independent problem state; the vector-of-RNGs overload copies a shared problem, whereas a caller-supplied vector of problems is used as given. The cooperative sampler shares a reparametrization across its chains and refits it from pooled evidence.

Build the pairs deterministically in the same order and with the same length when resuming. Checkpoint controls are restored positionally, so a matching model dimension does not establish that a reordered map is compatible. During inversion, a transformed coordinate used by another map's location or log-scale accessor must precede that dependent map.

The vector must retain a concrete rule type. Mixing constants and differently typed closures across pairs can widen that type and is rejected at construction. Closures created at one source location, for example in a comprehension, share a type. For heterogeneous blocks, one callable struct can represent either a coordinate lookup or a constant; the Reparametrization guide executes that construction. Every accessor argument must be a Real or callable.

WarmupHMC.ReparametrizedProblem Type
julia
ReparametrizedProblem(reparametrizer, problem, ad_backend=nothing; scoring_plan=nothing)

Wrap a LogDensityProblems target with a coordinate map from sampler coordinates (source) to the model's coordinates (target). The transformed density includes the map's log-Jacobian. Supply an IndexedReparametrization, or a custom reparametrizer controlled by a WindowSelectionPlan.

The inner target supplies its own gradient. ad_backend differentiates the map and Jacobian through DifferentiationInterface; load the implementing AD package as well. For Enzyme, load Enzyme and pass AutoEnzyme(). The two-argument constructor supports log-density evaluation but does not provide a sampling gradient. An empty indexed map is the identity and has no controls to adapt.

scoring_plan accepts a CandidateScoringPlan or WindowSelectionPlan. The default uses WarmupHMC's candidate rule. A custom plan is not serialized; reconstruct the same strategy when resuming a checkpoint. Its presence is checked during restoration.

Adaptive and cooperative sampling return posterior_position in the inner model's coordinates, including when nonlinear_adapt=false. Do not transform those returned positions again. Other working arrays retain sampler coordinates. See Reparametrization for construction and coordinate conventions.

Adaptation rules ​

WarmupHMC.CandidateScoringPlan Type
julia
CandidateScoringPlan(prepare, score; synchronize! = identity)

A pluggable strategy for scoring reparametrization candidates from online evidence, attached with ReparametrizedProblem(ir, problem, backend; scoring_plan = plan).

Every ReparametrizedProblem has a plan — the public nothing default resolves to an internal direct-scoring plan. Passing one therefore replaces a strategy rather than enabling one. Declining a pair is not the same as having no plan: score returning nothing restores the direct scoring formula for that pair, but attaching any custom plan already determines the evidence source, so a plan that declines every pair is still not equivalent to the default.

Callbacks

prepare(ir, position, gradient) runs once per online evidence observation and returns a transient frame. The frame is opaque to WarmupHMC and is passed unchanged to every score call arising from that observation, so it is where work shared across candidates belongs rather than being repeated per pair.

score(frame, pair_number, idx, reparametrization, candidate) returns (ljac, position, gradient) for candidate, where ljac is the log-Jacobian term in logdensity(rp, x) == ljac + logdensity(problem, y). pair_number is the pair's one-based position in ir.pairs; idx is that pair's source-vector coordinate selector. Returning nothing instead delegates that one pair to direct scoring; the choice is per pair, so a plan may score only the pairs it has an opinion about.

synchronize!(ir) runs DURING construction — inside ReparametrizedProblem's inner constructor, ahead of new, so the problem does not exist yet and ir is all a plan can reach — then after every winner commit, and when a checkpoint source is restored. Those are the points at which ir may have changed underneath a plan holding derived state. The default identity is correct for a stateless plan.

Evidence source

A custom plan interprets nonlinear_evidence=:linear_pool as online all-good-leaf evidence; it never replays the retained linear pool.

Checkpoints

Checkpoint payloads are Serialization-based and deliberately exclude the log-density and the scoring plan, so a plan does not survive a checkpoint. The marker is compared on restore and a mismatch is an error in either direction: restoring a plan-recorded run without attaching one, and restoring a default-recorded run with a plan attached, both fail loudly rather than falling back. A silent fallback would resume a different problem than the one recorded while looking like a successful restore.

See ReparametrizedProblem for the wrapper this attaches to, and candidate_scoring_losses for the criterion and the supported ways to inspect its loss curve.

WarmupHMC.candidate_scoring_losses Function
julia
candidate_scoring_losses(payload::NamedTuple)
candidate_scoring_losses(lpdf, positions, gradients; weights=nothing)

Return one row per reparametrized coordinate and candidate, with fields pair_number, index, candidate, loss, groups, and effective_n. candidate is the candidate partial-centering value on the fixed 0.0:0.1:1.0 grid. loss is missing until more than two evidence groups have accumulated, matching the sampler's selection threshold.

For finite, nondegenerate observations, the default candidate objective is

julia
L = w₁ * (-mean(Δlog|J|) + log(var(position)) / 2) +
    (1 - w₁) * cor(position, gradient),       w₁ = 0

so the selected candidate minimizes weighted position-gradient correlation. Writing W = sum(wᵢ), q̄ = sum(wᵢqᵢ) / W, and ḡ = sum(wᵢgᵢ) / W, that correlation is exactly

julia
sum(wᵢ * (qᵢ - q̄) * (gᵢ - ḡ)) /
sqrt(sum(wᵢ * (qᵢ - q̄)^2) * sum(wᵢ * (gᵢ - ḡ)^2))

The log-Jacobian/log-variance term is present but has zero default weight; a CandidateScoringPlan changes how candidate observations are constructed, not this criterion. WarmupHMC does not reject nonfinite candidate observations or losses. The implementation evaluates both displayed terms before applying the weights, so degenerate or nonfinite input can produce a nonfinite loss even at w₁ = 0; this function returns that value unchanged. The sampler's selection never picks such a candidate: it minimizes over the finite losses only, keeps a coordinate's current centering when none of its losses is finite, and warns which coordinates had a candidate excluded.

The payload method reads the serialized nonlinear_recorder accumulator from an adaptive or cooperative checkpoint. It is the actual pending online curve since the most recent nonlinear reset, not a history: after a restarting window selects a candidate, the recorder is reset before that boundary's checkpoint is written. Payloads without that recorder, including cooperative checkpoints (the merged sampler refits from pooled halos and keeps no recorder), raise an ArgumentError.

The matrix method deliberately recomputes a retrospective curve. positions and gradients must have identical dimension × observations shapes and be in the current sampler/source coordinate frame. The attached CandidateScoringPlan, when present, prepares its own candidate frame from each column. Each positive-weight column counts as one evidence group; zero weights are ignored and negative weights raise ArgumentError. This is the same scorer and criterion, but it is the recorded warm-up curve only if the caller supplies the exact online leaf stream, weights, and group boundaries. Ordinary saved halo or posterior matrices do not contain those boundaries, so their curves are retrospective diagnostics.

WarmupHMC.WindowSelectionPlan Type
julia
WindowSelectionPlan(select!; synchronize! = identity)

A pluggable rule that CHOOSES a reparametrizer's controls at every restarting warm-up window, attached with ReparametrizedProblem(ir, problem, backend; scoring_plan = plan).

It replaces the candidate grid and its position-gradient criterion entirely. WarmupHMC keeps the rest of the window lifecycle: collecting evidence, transporting the retained pool and the active point into the newly selected coordinates, the metric update that follows, and checkpointing. Unlike a CandidateScoringPlan, a selection plan also works with reparametrizers that are not an IndexedReparametrization (see Custom reparametrizers below).

Callbacks

select!(ir, positions, gradients) runs at a restarting window boundary. The columns of positions and gradients are equally weighted sampler states in the CURRENT source coordinates of ir (read-only; see Evidence). It may update ir's controls in place and returns true if it did, in which case the evidence and the active point are transported into the new coordinates, or false to keep the current ones.

synchronize!(ir) has the same role and call points as for a CandidateScoringPlan.

Evidence

With nonlinear_evidence = :linear_pool (the default) the evidence is the retained pool itself (at most recording_target states). With :all_good_leaves or :nuts_weighted it is recording_target states drawn with replacement from every NUTS leaf of the window, each leaf with probability proportional to the weight WarmupHMC's own scoring gives it (nonlinear_trajectory_weighting included), so repeated columns are expected. Unlike a scoring plan, a selection plan never remaps :linear_pool.

Custom reparametrizers

Besides IndexedReparametrization, any WarmupHMC.AbstractReparametrization can be adapted by a selection plan if it implements:

  • WarmupHMC.with_logabsdet_jacobian!(y, ir, x) -> (ljac, y), the source-to-target map and its log-Jacobian (this runs under AD on every gradient evaluation);

  • InverseFunctions.inverse(ir), an AbstractReparametrization computing the target-to-source map in the same way;

  • WarmupHMC.reparam_controls(ir), a serializable COPY of the current controls, and WarmupHMC.restore_reparam_controls!(ir, controls), which writes such a value back and throws if it cannot belong to ir;

  • optionally WarmupHMC.snapshot_reparametrization(ir), an independent copy with the same controls (default deepcopy).

Checkpoints

The plan itself is not serialized; re-attach it on resume, as for a scoring plan. The controls are written under the payload's reparam_sources key.
